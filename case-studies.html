01 / FLAGSHIPIN DEVELOPMENT

Agentic customer complaint system

Python 3.13Ollamaqwen3:4bpytestHuman oversight

Problem

Customer-service teams want AI to handle routine complaints, but an agent that can act freely can make costly mistakes that are hard to undo. The question I set myself: how much can an agent safely do on its own, and exactly where must a person step in?

Approach

  • A provider-independent agent loop in Python using only the standard library, with a defined contract for any model adapter.
  • A deterministic safety screen runs before the model: high-value requests (£100+), money-transfer wording, suspicious phrases, out-of-policy requests and ambiguous cases go straight to human review.
  • The model (local qwen3:4b through Ollama, loopback only, no API keys) can call just four read-only lookups. Every tool name and argument is validated, and anything unexpected ends the run.
  • A hard limit of eight model calls. Every failure path (provider error, malformed output, invalid tool call, iteration limit) escalates to a person.
  • The escalation record separates verified facts from successful lookups, with where each came from, from what the customer claimed.

Result

A working prototype with a full audit trace for every case, a pytest suite that runs without a model by using a fake transport, and a ten-case evaluation harness that runs against the local model. A browser port of the control flow runs on this site.

What I'd change

Running the harness against the small local model showed that the model's output format, not the safety logic, was the weak point: malformed responses were escalated safely, but more often than I'd like. Next I would enforce a stricter structured output schema, compare larger local models against the same cases, and track the escalation rate as a headline metric.

02 / GOVERNANCEITERATIVE

AI evaluation, safety & governance

PythonpytestJSON contractsScenario testing

Problem

"The tests pass" is not the same as "the agent behaves safely". I wanted to write down what each kind of decision is allowed to rely on, and then check whether the controls actually enforce it.

Approach

  • A taxonomy of five decision intents, from reporting an order's status to escalating for human review.
  • A workflow contract that lists the evidence each decision needs (verified records, applicable policy, review requirements) and the states that evidence can be in: verified, missing, failed, not found or unknown.
  • Nineteen hand-written synthetic scenarios, each with an expected classification, run through a deterministic gate that answers allow, block or unknown.
  • A reconciliation report comparing expected with actual, validated by pytest.

Result

Eleven scenarios classified correctly and none incorrectly. Eight are deliberately left unresolved because the contract cannot decide them yet, and the report says so rather than guessing. It also flagged five inconsistencies between my own taxonomy and contract, which is exactly the kind of gap the exercise was meant to expose.

What I'd change

Resolve those five inconsistencies, map individual claims in a response to the exact record fields that support them, and run the scenario matrix automatically on every change.

03 / INFRASTRUCTUREEXPLORATION

Local AI infrastructure

Ollama 0.40qwen3:4bWindows 11RTX 3060 Ti

Problem

I wanted to experiment with language models without paying per request or sending data to a third party, on hardware I already own.

Approach

  • Ollama serving qwen3:4b on 127.0.0.1:11434, on a Ryzen 5 5600X with 32 GB of RAM and an RTX 3060 Ti.
  • The agent's adapter only accepts loopback addresses and has no API-key setting, so nothing leaves the machine by accident.
  • Explored Open WebUI as an interface, and kept an optional authenticated provider in the code for comparison.

Result

The complaint agent and its evaluation harness run entirely on my own computer. The architecture diagram on this site was generated from the real code and machine setup, not drawn from memory.

What I'd change

Benchmark several model sizes against the same evaluation cases, measuring accuracy, escalation rate and response time, so the choice of model is based on evidence rather than what happened to be installed.

04 / PRODUCTIVITY TOOLPROTOTYPE

AI graduate job finder

Transparent scoringJavaScriptnode:test

Problem

Job recommenders rarely explain why a role was suggested, so a graduate cannot tell what would make them a better fit. I wanted a match score where every point can be traced.

Approach

  • A weighted score out of 100 from five components: skills, location and work mode, salary, sector and level. Each comes with a plain-English reason.
  • Weights are adjustable, missing skills are listed, and each role links to a live search for similar real jobs.
  • The idea started as a Python scoring prototype; the version on this site is an interactive browser demo using fictional roles.

Result

A live demo with 22 fictional roles, 35 skills and seven job boards, backed by automated tests for the scoring rules and data.

What I'd change

Use real listings through a job-board API, which needs a small server to keep keys private; let people mark good and bad matches to tune the weights; and read skills from a CV inside the browser.

05 / WEB APPPUBLISHED

GUESSED, a daily guessing game

HTMLCSSJavaScriptGitHub Pages

Problem

Build a daily game that everyone plays and shares, with the same questions for everyone, but with no server, accounts or database.

Approach

  • The date in UK time is hashed to pick one question per category from a 117-question bank, so everyone gets the same five questions without a server.
  • Five question types with their own input: a price, a slider for size and distance, a percentage, a multiple-choice crowd prediction and a year.
  • Each answer scores 0 to 100 from how far off it was. Every question links to its source, and the crowd answers come from real YouGov polls.
  • Daily streaks, personal stats and a shareable result image, all saved on the player's device.

Result

Published and playable, including inside this portfolio. A later code review found a bug where a variable named performance hid the browser's own timer, so every result showed a score of zero, plus some emoji corrupted by a text-encoding mistake. Both are fixed, and the script is now structured so that class of bug cannot recur.

What I'd change

The crowd questions began as simulated placeholder data; they now use real YouGov polls, with each figure checked against the original article. Some of those polls date from 2011 to 2016, so next I would refresh them with newer data and add an archive so players can catch up on missed days.

06 / DISSERTATIONRESEARCH

Agentic AI & autonomous business processes

Resource-based viewSocio-technical systemsAgency theory

Problem

Organisations hear a lot about agentic AI, but have little to help them decide where autonomy is appropriate, and what capabilities they need before handing work to an agent.

Approach

  • Dissertation research on how agentic AI could change business processes, using the resource-based view, socio-technical systems and agency theory.
  • Connected to practice through the complaint-agent prototype, which tests bounded autonomy and human oversight in a real workflow.
  • Turned those lenses into an interactive readiness scorecard: ten answers, four scores, two safety gates and a "least autonomy that does the job" rule.

Result

A working decision aid on this site. Its complaint-triage example recommends a bounded agent with human oversight, the same design choice the prototype makes.

What I'd change

Calibrate the scorecard's thresholds against the dissertation's findings and real organisational examples, and test it with people who make these decisions at work.
